# CLAUDE.md

This file provides working instructions for Claude Code in the Midpoint website repository.

## Product and design direction

Midpoint is an architectural materials and solutions company based in Baghdad, Iraq. The website
should feel editorial, premium, precise, calm, and architectural. It should communicate expertise
and trust without looking like a generic SaaS landing page or an over-designed template.

Use the existing visual language: restrained navy and blue accents, paper-like backgrounds,
editorial typography, generous whitespace, hairline borders, strong image composition, and subtle
reveal animations. Preserve the established design system unless a change is explicitly requested.

## Stack and architecture

- Next.js App Router under `app/`.
- Next.js 16.3.5, React 19.2.8, TypeScript 5, strict mode enabled.
- Tailwind CSS v4 via `@tailwindcss/postcss`.
- Global styles and brand tokens are in `app/globals.css`.
- Path alias `@/*` resolves to the repository root.
- Shared UI and animation components live under `components/`.
- Content collections are primarily stored in `data/`.
- Static media lives under `public/` and must be verified before use.

Important existing routes include `/`, `/about-us`, `/brands`, `/products`, `/projects`,
`/services`, and `/contact-us`.

## Existing components to reuse

Before creating a new component, inspect and reuse the closest existing abstraction. Important
shared components include `PageHero`, `RevealText`, `RevealImage`, `SectionLabel`, `PhilosophyWords`,
`Arrow`, `ContactCta`, the layout components, and the existing UI primitives.

Do not duplicate animation, spacing, button, typography, or responsive-layout logic when an existing
component already provides it. If a shared component truly needs a new capability, keep the API
backward-compatible and update all affected call sites.

## Implementation rules

1. Start by reading the target route, its direct child components, relevant data files, global styles,
  and the nearest neighboring page. Form a specific hypothesis about the change before editing.
2. Keep changes focused on the requested feature. Do not rewrite unrelated routes, rename public
  paths, replace the design system, or add dependencies without a clear technical reason.
3. Use semantic HTML, meaningful headings, descriptive image `alt` text, visible keyboard focus,
  usable links, and sufficient color contrast.
4. Design mobile-first. Check narrow mobile, tablet, and wide desktop layouts. Prevent horizontal
  overflow, clipped text, unstable image dimensions, and overlapping content.
5. Use real assets from `public/`. Never invent asset paths. If a requested asset is missing, use an
  existing appropriate asset or clearly report the missing asset instead of hiding the problem.
6. Preserve `prefers-reduced-motion` behavior and avoid adding animation that blocks content access.
7. Do not invent company facts, metrics, partners, awards, addresses, or claims. Use verified content
  from the repository or mark new copy as content that requires client approval.
8. Keep metadata accurate for every changed route, including title and description where relevant.
9. Avoid unnecessary rounded cards, decorative gradients, excessive shadows, stock-style imagery,
  giant marketing hero sections, and repetitive card grids. Every section should have a clear job.
10. Do not add code comments unless they explain a non-obvious constraint or decision.

## Content and UX standards

- Keep public-facing website copy in English unless the task explicitly requests another language.
- Prefer concise, specific copy over vague marketing language.
- Use clear calls to action that match the destination, such as exploring brands, viewing projects,
  or contacting Midpoint.
- Use stable visual hierarchy: eyebrow or section label, heading, supporting copy, then action.
- Preserve the editorial pacing between sections and avoid making every section look like a card.
- Treat images as part of the information architecture: choose assets that help explain materials,
  spaces, products, or projects.

## Validation workflow

After every substantive edit:

1. Run the narrowest relevant check first.
2. Run `npm run lint`.
3. Run `npm run build` for route, metadata, layout, or shared-component changes.
4. If a dev server is available, inspect the changed route at desktop and mobile widths and check
  the browser console for errors.
5. Report exactly what changed, which checks passed, and any remaining limitation or missing content.

There is currently no test runner configured, so do not claim that tests passed when only lint/build
were run.
